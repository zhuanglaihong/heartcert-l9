# 归心 L9 动态出题引擎底层重构执行指令 (Final V1.0)


**核心目标：** 彻底废弃静态题库，建立基于「1024 原子能力库」与「元模板 (Meta-Blueprint)」驱动的多模态动态沙盒引擎，并实现 Oracle Judge 的受控向量输出。

## 第一战区：底层数据结构重塑 (Data Foundation)
**绝对禁止使用动态生成的字符串作为能力标签。** B 端搜索的准确性建立在严苛的底层数据纪律之上。

1. **确立神谕底座 (The 1024 Atoms)：** - 新建表 `ability_library`。写入并锁死 1024 个不可再分的原子技术/业务能力（ID 从 0001 到 1024）。
2. **构建岗位映射视图 (Role Schemas)：**
   - 新建表 `role_schemas`。预设各核心岗位（如 AI 后端、AI 产品）的 6 大考核维度。
   - **硬性约束：** 必须明确定义这 6 大维度由 `ability_library` 中的哪些具体 ID 加权构成。
3. **高维能力原油池：**
   - 修改候选人主表 `candidates`，彻底废弃旧的 `skills` 文本标签字段。
   - 新增 `capability_vector` 字段，类型强制设定为 `vector(1024)`（需安装 `pgvector` 插件）。每一维的 Index 严格对应 `ability_library` 的 ID。

## 第二战区：全链路 Agent 调度总线 (The Pipeline)

### 阶段一：DNA 提取与蓝图下发 (Ingestion & Dispatch API)
* **触发机制：** 候选人选择考核岗位并上传简历。
* **数据输入：** 原生态简历文本 + 用户自选方向。
* **系统动作：**
  1. 系统从 `role_schemas` 提取该岗位对应的原子能力 ID 集合。
  2. **Ingestion Agent** 将简历内容与这些 ID 进行比对，输出一个稀疏 JSON 作为候选人的初始能力快照 `Candidate_DNA.json`。
  3. 系统提取对应的 **元模板 (Role_Blueprint Prompt)**。
* **数据透传：** 将 `Candidate_DNA` 与 `Role_Blueprint` 组合，下发给第二阶段。

### 阶段二：深渊战役渲染与 X-RAG 绞肉机 (Battlefield API)
这是 L9 引擎的灵魂，**严禁生成常规的八股文问答**。根据 `Role_Blueprint` 的定义，分化为两条核心执行链路：

**链路 A：代码/工程岗 (Sandbox Mode)**
* **战役渲染：** Battlefield Agent 根据候选人 DNA 中的优势语言，凭空捏造一套包含完整 Markdown 文档的【归心私有 RPC 框架】或【带有死锁/内存泄漏的残缺工程】。
* **X-RAG 实时对抗：**
  - 基于 WebSocket 监听候选人 IDE 内的代码 Diff。
  - **触发条件：** 代码运行通过测试用例，或停留超过 60 秒。
  - **攻击方式 (异常注入)：** X-RAG 强制在后台修改运行环境（如：模拟 Redis 节点宕机），并弹出模态框要求候选人即时重构降级策略。

**链路 B：产品/架构岗 (Interview & PRD Mode)**
* **战役渲染：** 生成极其尖锐的业务矛盾场景（例：“大模型推理成本超标 300%，但客户拒绝精度下降，你只有 10 分钟出具架构调整 PRD”）。
* **X-RAG 实时对抗：**
  - 抓取候选人的语音/文本输入。
  - **攻击方式 (逻辑压迫)：** 识别回答中的逻辑漏洞或资源悖论，生成极具压迫感的多轮追问，极限测试其 Context Engineering 能力。

### 阶段三：神谕确权与高维降临 (Oracle Judge API)
**绝对禁止大模型自由发挥打分。**

* **数据输入：** - 第一阶段提取的 `Role_Schemas`（预设的原子能力 ID 列表）。
  - 第二阶段产生的完整 `Battle_Log` (代码 Diff、X-RAG 追问问答对、耗时 TTR)。
* **系统动作 (受控打分)：** 强制 Judge Agent 仅针对 `Role_Schemas` 中规定的原子能力 ID 进行 0.0 到 1.0 的评分，严禁生成库外能力。
* **数据落盘：** - 生成 1024 维的特征向量，永久覆写至 `capability_vector` 字段。
  - 提取高光对抗切片，存入 `JSONB` 字段，用于前端雷达图和防伪报告渲染。

架构审计已启动。作为 Principal Architect，针对归心 L9 “多模态出题与混合检索一体化”底座，以下是无修正的工程解剖与重构法典。

---

### 一、 漏洞狙击 (Red Teaming)

当前架构虽然在概念上实现了业务闭环，但在高并发沙盒和底层数据侧存在三个致命的工程级崩溃点：

1. **Token 爆炸与 X-RAG 调度死锁：**
   * **缺陷：** 基于 WebSocket 监听 IDE 代码 Diff 并触发大模型追问，是极其危险的做法。AST 探针即使只监听“核心逻辑修改”，在候选人频繁保存或试错时，仍会导致并发 API 请求风暴
   * **修正：** 引入 **Debounce (防抖) 与 Checkpoint (里程碑) 机制**。X-RAG 不应由代码 Diff 频次直接驱动，而应由“测试用例执行失败的 Error Log”或“特定时间窗口（如每 5 分钟）内的重构增量”触发。
2. **1024 维向量的稀疏性灾难：**
   * **缺陷：** 候选人主表 `candidates` 引入 1024 维的 `capability_vector`。由于绝大多数开发者只具备其中 20-50 项核心能力，该向量将是一个极其稀疏的矩阵（大量 0.0）。在使用 pgvector 计算余弦相似度时，高维稀疏向量容易出现“维度诅咒”，导致召回精度急剧下降。
   * **修正：** `capability_vector` 的生成必须包含**平滑化处理**（对未考核的强相关弱连接能力赋予基线微小权重，而非绝对的 0），或者在查询阶段使用带阈值的 Masking 机制。
3. **混合检索内存 OOM (Out Of Memory) 风险：**
   * **缺陷：** RRF 倒数秩融合算法在后端平滑合并双路结果时，如果在数据库层面各自召回 Top 1000 然后传给后端 Server，会造成严重的网卡和内存拥堵。
   * **修正：** “双轨并发召回” 必须只向后端返回 `(candidate_id, rank)` 对，禁止在此阶段拉取 `reranker_payload` 或全量 JSONB。仅当 RRF 计算出最终的 Top 50 后，再通过一次 `IN` 查询拉取重排弹药。

### 二、 核心状态机与边缘逻辑补全 (State Machine & Edge Cases)

从 C 端鉴权到 B 端流转，缺失了核心的状态转换与降级防线。

1. **L9 战役生命周期 FSM (有限状态机)：**
   系统缺乏明确的沙盒生命周期管理。需强制引入以下状态流转：
   * `PROVISIONING` (捏造私有框架中) -> `COMBAT_ACTIVE` (沙盒对抗中) -> `EVALUATING` (微观快照与 Judge 打分中) -> `CERTIFIED` / `FAILED`。
   * **防线：** 如果 `PROVISIONING` 阶段大模型超时超过 15 秒，必须降级到预存的 `Fallback_Blueprint`（静态备用残卷），确保候选人体验不断档。
2. **能力向量的半衰期衰减 (Vector Time-Decay)：**
   技术能力是有保质期的。三年前的 1.0 评分不能等同于今天的 1.0。
   * **修正：** 在 B 端的 `Target_Vector` 召回公式中，引入时间衰减因子 $\lambda$。检索时的实际打分为计算相似度后乘以 $e^{-\lambda \Delta t}$，其中 $\Delta t$ 为距离最后一次 L9 战役的月数。

### 三、 终极重构法典 (Execution Spec)

严格基于 PostgreSQL 15+ 与 pgvector。

#### 1. 核心 DDL 约束 (Data Definition)

```sql
-- 开启向量插件
CREATE EXTENSION IF NOT EXISTS vector;

-- 原子能力库 (绝对静态，由迁移脚本维护)
CREATE TABLE ability_library (
    atom_id SMALLINT PRIMARY KEY CHECK (atom_id BETWEEN 1 AND 1024),
    skill_name VARCHAR(64) UNIQUE NOT NULL,
    domain VARCHAR(32) NOT NULL
);

-- 候选人能力主表
CREATE TABLE candidates (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    -- JSONB 存储硬标签，强制结构为 {"verified_skills": ["Golang", "Redis"], "reranker_payload": "..."}
    profile_data JSONB NOT NULL DEFAULT '{}'::jsonb,
    -- 1024维能力向量，严格对应 ability_library
    capability_vector vector(1024),
    last_certified_at TIMESTAMPTZ,
    CONSTRAINT chk_profile_data CHECK (jsonb_typeof(profile_data->'verified_skills') = 'array')
);

-- 构建倒排与向量索引
CREATE INDEX idx_candidates_profile_gin ON candidates USING GIN (profile_data);
-- 强制使用 HNSW 提升稠密召回效率
CREATE INDEX idx_candidates_vector_hnsw ON candidates USING hnsw (capability_vector vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

#### 3. B 端工业级混合检索 (Hybrid Search) 算法管线

要求 1.5 秒内返回结果，逻辑执行顺序如下：

**Step 1: 意图降维**
Query Parser Agent 并行输出：
1. `Target_Vector` = `[0.0, ..., 0.9, ..., 0.0]` (1024维)
2. `Extracted_Tags` = `["高并发", "Redis", "死锁"]`

**Step 2: 双路极速召回 (PostgreSQL 内存计算)**
使用 CTE (Common Table Expressions) 一次性拉取双路 ID 集合：

```sql
WITH sparse_recall AS (
    SELECT id, row_number() OVER (ORDER BY ts_rank(to_tsvector('english', profile_data->>'verified_skills'), plainto_tsquery('english', '高并发 Redis 死锁')) DESC) as rank
    FROM candidates
    WHERE profile_data @> '{"verified_skills": ["Redis"]}'
    LIMIT 200
),
dense_recall AS (
    SELECT id, row_number() OVER (ORDER BY capability_vector <=> '[0.0,...]'::vector) as rank
    FROM candidates
    ORDER BY capability_vector <=> '[0.0,...]'::vector
    LIMIT 200
)
```

**Step 3: RRF 融合计算 (Backend Server)**
在后端内存中提取上述结果的 ID，使用 RRF 公式（常量 $k$ 建议设为 60）：
$$RRF_{score}(d) = \frac{1}{60 + rank_{sparse}(d)} + \frac{1}{60 + rank_{dense}(d)}$$
提取 $RRF_{score}$ 最高的 Top 50 个 `id`。

**Step 4: Cross-Encoder 重排绝杀**
通过 `SELECT profile_data->>'reranker_payload' FROM candidates WHERE id IN (...Top 50)` 获取弹药。
调用 BGE-Reranker 模型，将原始查询词与 50 条 payload 进行 Cross Attention 计算，按 Logits 降序输出最终 Top 3 给到 HR 页面。
