**PRD 定位**

这版不是“想法说明”，而是按你当前仓库可落地的底层重构标准写的架构方案。它基于现有搜索入口 [search.py](/Users/tylor/Code/heart%20dev/HERTCERT/guixin-cert/apps/api/src/routers/search.py)、现有两阶段检索链路 [pipeline.py](/Users/tylor/Code/heart%20dev/HERTCERT/guixin-cert/apps/api/src/services/search/pipeline.py)、现有混检实现 [hybrid_search.py](/Users/tylor/Code/heart%20dev/HERTCERT/guixin-cert/apps/api/src/services/search/hybrid_search.py)、现有评分编排 [orchestrator.py](/Users/tylor/Code/heart%20dev/HERTCERT/guixin-cert/apps/api/src/services/scoring/orchestrator.py) 和现有维度向量发布逻辑 [update_candidate_vector.py](/Users/tylor/Code/heart%20dev/HERTCERT/guixin-cert/apps/api/src/services/vector/update_candidate_vector.py)。

**目标**

把“题目级能力贡献”从现在的结果态模型，升级成可回放、可撤销、可聚合、可分层检索的事件账本模型。系统最终输出四类资产：

1. 测试会话分数资产：单题、单能力、单场测试、全局候选人。
2. 三层能力向量资产：1024 原子层、128 能力族层、32 宏观层。
3. 分层召回资产：32 粗召回、128 中召回、1024 精召回。
4. rerank 资产：基于需求原文和候选人证据包的最终排序。

**一、核心设计原则**

1. “分数”与“向量”分离。分数用于解释，向量用于召回。
2. 候选人全局画像不能直接覆盖写死，必须由来源事件重算。
3. 重做不是 update 一条总分，而是替换某次 assessment 的贡献快照。
4. 1024 维不直接做全库粗搜，只做末层精排。
5. 企业需求侧也必须落成三层目标向量和标签权重快照，不能只留 query_text。

**三、分数与向量计算标准**

1. 单题掌握度  
`question_mastery = Σ(weight_i * normalized_score_i)`

2. 单题得分  
`question_final_score = question_mastery * question_full_mark`

3. 单场测试内 1024 聚合  
V1 标准：
同一 `assessment_id` 下，同一 `ability_id` 的多个题目贡献，采用 `weighted_mean(contribution_score, question_weight)`  
不要用裸均值，第一版就该上加权均值，否则 5 分题和 10 分题影响一样，失真。

4. 跨测试聚合  
V1 标准：
同一 `candidate_id + ability_id`，按 `assessment_ability_aggregates.score` 做均值。  
V2 可升级成：
`EMA` 或 “最近一次权重更高”。

5. 128/32 汇聚  
统一用 `ability_taxonomy_edges.weight` 做加权汇聚。  
禁止手写 if/else 映射散落在代码里。

**四、重做与回放机制**

1. 某 assessment 重做时，先把 `candidate_ability_contributions` 对应 `assessment_id` 的 `is_active=false`。
2. 写入新一版 `question_ability_scores`、`assessment_ability_aggregates`、`candidate_ability_contributions`。
3. 只重算受影响 candidate 的 `candidate_ability_snapshots` 和 `candidate_vectors`。
4. 不允许直接 update `candidate_vectors` 而不保留 contribution 记录。
5. 每次重算都带 `vec_version` 和 `grader_version`，便于线上排错。

**五、混合检索路由机制**

你现在的 Stage1 是“向量召回 + 文本召回 + RRF”，但还是单层 skill/dimension 视角。重构后改成四段路由：

1. Filter Gate  
先走硬过滤：城市、远程、薪资、经验、学历、私有池、可见性。  
这一层保留在 SQL/RPC。

2. L1 粗召回，32 维  
RPC：`search_candidates_by_vec32(profile_id, limit, filters)`  
目标：从全量候选人里快速找方向对的人。  
返回 top 200。

3. L2 中召回，128 维  
RPC：`search_candidates_by_vec128(profile_id, candidate_ids, limit)`  
只在 L1 结果集上跑。  
返回 top 80。

4. L3 精召回，1024 维 + 稀疏标签  
RPC：`search_candidates_by_vec1024(profile_id, candidate_ids, limit)`  
外加 `must_have_abilities` 做 hard boost / hard drop。  
返回 top 40。

5. Sparse Text Recall Sidecar  
保留你现有全文召回，但从“主召回路径”降级成“补漏路径”。  
只对 L1/L2 没覆盖到的候选人补充召回，避免文本噪声主导排名。

6. Fusion  
L1/L2/L3/Text 四路统一走 RRF，但权重分层：  
`0.15 * score32 + 0.25 * score128 + 0.40 * score1024 + 0.20 * sparse_text_score`  
这一步输出 top 30 进入 rerank。

**八、迁移顺序**

1. 先建 taxonomy 和 contribution 表，不切线上读路径。
2. 再让新评分链路双写：旧表继续写，新表同步写。
3. 回填历史 assessment 为 `candidate_ability_contributions`。
4. 生成 `candidate_vectors` 三层向量。
5. 上新搜索 pipeline，灰度比较旧搜索和新搜索。
6. 稳定后再把 `candidates.skill_vector` 降级为兼容字段。

**九、验收标准**

1. 任一候选人的任一能力值，都能追溯到具体 assessment 和具体题目。
2. 同一 assessment 重做后，不会重复累计旧贡献。
3. 搜索请求能保存 profile，并可重放。
4. 检索链路日志能看到每层召回数量、分数和淘汰原因。
5. rerank 结果能解释为什么 A 排在 B 前。
